# 额度与智能一起编排（0.24）

目标是在达到验收标准的前提下，减少完成整个任务所需的模型工作、返工和主会话协调。
不能从模型名或 API 标价推出订阅额度的最优解。下面是已应用的路由规则和主 agent 的
执行指引；它没有新增一个付费分类模型，也没有另起一个自动 DAG 调度器。

## 为什么改变

之前先按模型档位、家族偏好删候选，随后才比较 token 与额度。即使另一个合格模型
额度充足、同类任务的历史完成成本更低，它也可能在比较前被删掉。每个 provider 只取
偏好排序前四个模型也会掩盖后面的经验候选。0.24 在计算成本前保留全部合格模型，
展示结果时才限制候选列表大小。

## 自动选择的实际顺序

1. 先检查授权池、工具、输入路径、能力下限、支持的 effort、冷却与额度保留线。
   显式选定的角色／模型／effort 继续遵从调用方；auto 不会越过角色或账号权限。
2. 比较预计完成 token：有足够同类且已验收／失败的数据时计入失败尝试与主线程交接；
   样本不足用标明 bootstrap 的估算。各订阅额度、API 金额、缓存 token 不换算成同一种钱。
3. 只在最低预计 token 的 115% 范围内做额度择优。这个 15% 是允许的小幅估算工作量
   交换，不是承诺实际消耗只增加 15%，也不是账单或运行中硬上限。
4. 该范围内有已知剩余至少 40% 的候选时，暂缓选择已知剩余不超过 20% 的候选。
   没有 reset 时间也能识别这种压力差；unknown 不被假定充足或耗尽。
5. 在剩余候选中按合适的档位、用户偏好的模型家族择优；然后比较限制窗口的重置临近程度、
   已知剩余额度和估算 token。同模型两个账号可因此使用余量更大的已授权账号。

既有主会话保留策略先于这个比较：preserve-parent／preserve-claude、关键低额度、
大量工作时主额度不超过 20% 仍可排除主会话。计划用 parent_reserved 标明。
极小、明确的工作仍留在主会话；有合格快档 worker 时，不让强档主会话吞掉大量机械工作。
冷启动估算会倾向保留普通短任务在主会话，不能据此声称真实主模型成本更低。

状态里的 model_policy.selection 和计划里的 selection_policy 展示阈值、比较数量、
被暂缓的 provider 及成本范围；candidates 保留首选和其他可行方案，避免只看到一个模型。
这些阈值是当前保守策略，不是经过跨模型实验得到的最优值。

## 主 agent 如何分配阶段

主 agent 在当前轮一次性判断 task_profile，不逐步启动分类器或规划 agent。
assessment.orchestration／task_assessment.orchestration 给出与当前评估一致的执行建议：

| 情况 | 工作方式 | 初始模型偏好 |
| --- | --- | --- |
| 极小查找、直接回答 | 主会话完成 | 当前模型 |
| 明确输入、机械操作、既定检查 | 一名 owner 完成整个可验收单元 | Terra / low；文件处理可用 DeepSeek Flash / low |
| 范围明确、低风险且低不确定性的代码小改动，有明确测试 | 快档实现并执行测试 | Terra / low |
| 常规实现、一般调试、边界明确的评审 | 实现和确定性验证放在同一工作单元 | Sol / medium |
| 接口未知、架构决策、证据冲突 | 先解决不确定性、冻结接口和验收，再分配实现 | Astra / high；具体可用模型仍服从目录 |
| 高风险变更 | 完成后独立检查风险点及确定性证据 | 满足风险下限的 reviewer |

不要因为整个项目复杂，就把每个后续任务都标成复杂；也不要仅因为做过规划，就降低
后续步骤仍然存在的风险。模型／effort 的变化安排在真实阶段边界，各阶段独立评估。
当前高风险／高不确定性仍保留复杂能力与 high effort 下限；auto 最大 xhigh。
同一 work_item 失败重试保留下限，不能重命名来绕过次数或升级约束。

例如量化研究任务：Astra 明确数据、公式及因果边界；Sol 实现既定逻辑；Terra 执行
已给定的检查并产出证据；DeepSeek 整理可访问的报告材料。涉及统计推断、交易正确性
或不明确口径的检查不能仅因叫作“测试”就归为机械任务。file-only DeepSeek 不能运行
Python、replay 或访问其 cwd 以外的 brief；需要 shell 的阶段必须分给具备工具的角色。

## 控制整个任务的协调开销

- 每个 owner 接收目标、所需输入、允许修改范围、验收条件、返回产物和失败时的停止条件。
- 只有输入已就绪、无依赖且写入范围不冲突的任务才并行；仍服从已配置的并发数。
- 强模型产出的接口、假设、拒绝方案及证据路径可交给后续 owner；不复制整段会话。
- 主会话读摘要和验收证据，不再重复实现子任务。普通进度交给程序 waiter，不反复催问模型。
- 默认一个实现 owner；明确的局部修复先续用原会话。输入缺失、权限、基础设施失败先修环境；
  只有真正的质量失败才触发模型／effort 升级。不要用反复换模型掩盖错误任务说明。
- 高风险或项目规则要求的独立评审必须保留。其余任务优先确定性测试和主会话核验；没有
  新问题时不添加第二、第三轮模型评审。验收冲突明确报告，不能为了省额度弱化标准。
- 持久任务／loop 继续使用原预算、最大轮数和父会话监督；这里的建议不会自动启动循环。

## 验证与依据

验收前固定输入和质量标准，比较整条路径的 worker token、主线程协调、失败尝试、
修复时间及完成质量。已有真实任务可形成样本，不为了“训练路由”自动重复付费任务。
本轮采用确定性路由与模拟目录／额度回归验证，没有测得真实节省百分比或跨模型胜率。

参考 [OpenAI 模型选择](https://developers.openai.com/api/docs/guides/model-selection)：
按相同输入、质量标准与 effort 比较，并统计复核／返工时间。
参考 [Anthropic 的编排模式](https://www.anthropic.com/research/building-effective-agents)：
按任务需要拆分、并行和迭代，使用清楚的评价条件。这里只采用这些设计原则，
没有把早期文章中的框架细节视作当前宿主功能。
